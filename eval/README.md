# 점수판 (eval) — 프롬프트·생성 로직을 고칠 때 나빠지지 않았는지 재는 자

> 사용자 기능이 아니다. 개발용 자다. "어떤 사업 정의서를 받아도" 잘 뽑는 게 목표이므로
> 정답 세트는 사업마다 하나씩 늘리고, **모든 세트의 점수를 함께** 본다.

## 구성
```
eval/
  sets/<사업>/
    input.txt     정의서 원본 텍스트 (HWP → 한컴 COM으로 뽑은 전체. 일부 발췌 금지)
    gold.json     실제 납품 EAP에서 뽑은 정답 (scripts/ea-export-gold.ps1)
    actors.txt    액터 사전 (gold.json의 actors, 한 줄에 하나)
  score.ts        점수 계산
  results/<날짜>.json   실행 결과 (git 포함 — 추세를 본다)
```

## 점수 (세트마다, 그리고 전체 평균)
| 항목 | 뜻 | 어떻게 |
|---|---|---|
| **구조** | 요구사항 행을 제대로 읽었나 | 기능 행 수, 패키지(SFR-NNN) 수, 다이어그램(하위 번호) 수가 정답과 같은가 — LLM 전 단계(extract)의 점수 |
| **유스케이스 재현율** | 정답 21개 중 몇 개를 만들었나 | 이름의 핵심 명사 겹침 ≥ 0.5면 같은 것 |
| **유스케이스 정밀율** | 만든 것 중 정답에 없는 것 | 위와 같은 기준 |
| **요구사항별 개수 차이** | 어느 요구사항이 얇고 어느 게 부풀었나 | 정답 수 − 생성 수, 요구사항별 표 |
| **액터 배정** (사전 줌) | actors.txt를 주고 돌렸을 때 유스케이스↔액터 연결이 맞나 | 연결 쌍 일치율 (짝지어진 유스케이스만 — 재현율이 낮으면 같이 낮다) |
| **배정 (요구사항별)** | 정답이 요구사항마다 쓴 액터를 생성도 그 요구사항에 썼나 | 쌍 일치율. 유스케이스 이름을 못 맞혀도 "누가 하는 일인지"를 잰다 |
| **액터 추출** (사전 없음) | 사전 없이 돌렸을 때 액터 이름을 얼마나 맞히나 | 참고용. 원본에 이름이 거의 없어 낮은 게 정상 |
| **include / extend** | 관계 맞힌 수 | n/m |

두 번 돌린다: 사전 있음 / 사전 없음. 커밋 기준은 **사전 있음** 점수다 (실사용이 그 쪽).

## 원칙
- 프롬프트·생성 로직을 바꿀 때는 전후 점수를 비교해, **전체 평균이 오를 때만** 반영한다.
- 한 세트만 오르고 다른 세트가 떨어지면 버린다 (그 사업에만 맞춘 것이다).
- 프롬프트에 세트의 사업 단어(소상공인, 지원사업…)를 넣지 않는다.
- 정답에 없는 지식(액터 이름)을 LLM이 지어내게 하지 않는다.

## 새 사업 세트 넣는 법
1. 정의서 HWP → `powershell scripts/hwp-to-text.ps1 -Hwp <파일> -Out eval/sets/<사업>/input.txt`
2. 납품 EAP → `powershell scripts/ea-export-gold.ps1 -Eap <파일> -Out eval/sets/<사업>/gold.json`
3. `actors.txt`는 gold.json의 actors에서 복사
4. `npm run eval` — 모든 세트를 자동으로 찾는다
